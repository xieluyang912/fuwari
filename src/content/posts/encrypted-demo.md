## 怎么给一篇文章上锁

只要在 frontmatter 里加一行 `password`：

```yaml
---
title: 我的私密文章
published: 2026-10-06
password: "你的密码"
passwordHint: "可选，明文显示在密码框下面"
---
```

保存、重新构建，这篇就锁上了。`passwordHint` 不填也行。

另外还有一个保险字段 `encrypted`：写了 `encrypted: true` 却不填密码，构建会直接失败。
这是故意的 —— 比静默地把一篇本该加密的文章当明文发出去要好。

## 它会藏起什么

只填了密码，就等于承认「这篇要挡住路人」。那么任何**从正文推导出来**的东西
都不该再露在外面，所以下面这些也被一起处理了：

| 位置 | 正常文章 | 加密文章 |
| --- | --- | --- |
| 列表页摘要 | `remark-excerpt` 从正文抽的摘要 | 换成一句「本文已加密」 |
| 列表页字数 | 显示 | 不显示 |
| 文章页目录 | 全部小标题 | 不显示 |
| 文章页字数 / 阅读时长 | 显示 | 换成「已加密」徽章 |
| RSS | 全文 | 一句提示 + 标题前的 🔒 |
| Pagefind 搜索 | 全文可搜 | 只索引标题 |

因为标题是**你自己写在 frontmatter 里**的，本来就是要给人看的，
所以它照常显示 —— 列表里也会带一个小锁图标。

## 加密是怎么做的

整条链路是「构建时加密，浏览器里解密」：

1. 构建时，Astro 把正文渲染成 HTML 字符串；
2. 用 `PBKDF2-SHA256`（31 万次迭代）从密码派生出一把 `AES-256-GCM` 密钥；
3. 加密，把密文写进页面。**明文从头到尾没有离开过构建进程的内存**；
4. 访客输入密码后，浏览器用 Web Crypto 现推密钥、解密、把 HTML 注入页面。

密码对不对不靠比对哈希 —— AES-GCM 是带认证的，密码错了就解不开，直接抛错。
这样页面里不留任何可以拿来比对的东西。

### 几个刻意的设计

- **盐和 IV 每次构建都重新随机**：同一篇文章、同一个密码，两次构建出的密文完全不同。
  这是 AES-GCM 的硬性要求，IV 重用会直接破坏它的安全性。
- **密文和文章绑定**：加密时把 `post:<文章 id>` 作为 AAD 一起纳入认证计算。
  把 A 文章的密文复制到 B 文章的页面上解不开。
- **解锁状态只存密钥，不存密码**：存在 `sessionStorage`（关掉标签页就没了），
  而且缓存的是派生结果，下次站内翻回来不用重跑那 31 万次迭代。
- **密码不进前端**：密码只在构建时用来加密，不会以任何形式出现在页面或 JS 里。

:::caution
说句实话：静态站点没有后端，**密文是公开的**，任何人都能把它下载下来离线暴力破解。
PBKDF2 迭代 31 万次能把成本抬高不少，但密码本身太弱（比如 `123456`）依然会被秒破。

这个功能的定位是「挡住随便点进来的访客」，不是对抗有动机的攻击者。
真正的机密、密钥、别人的隐私，不要往上放。
:::

## 已知没做的部分

解锁之后，右侧目录不会自动重建 —— 目录是服务端根据 `headings` 生成的，
而加密文章的 `headings` 是空的。要补的话得在解密成功后用 JS 把 `h2` / `h3` 扫一遍重新生成。
目前留空，反正解锁前它本来就是空的。
